A system design where components communicate through events rather than direct calls. Key Characteristics:
1. Asynchronous processing.
2. Loose coupling.
3. Scalability and flexibility.
Why use it?
- Enhances system response.
- Enables real-time event processing.
- Supports complex workflows.

### Asynchronous vs synchronous systems
1. Synchronous Communication:
	1. Blocking calls.
	2. Tight coupling.
	3. Traditional HTTP APIs.
2. Asynchronous Communication:
	1. Non-blocking.
	2. Decoupled components.
	3. Message queues and event brokers.

Asynchronous introduce a design complexity but create flexible, resilience and scalability required by many modern distributed systems.

Pub-Sub vs. Event Streaming
- Publish-subscribe Model:
  1. Events are broadcasted to multiple subscribers.
  2. Each subscriber gets the events once.
- Event Streaming:
  1. Events are stored and consumed in order.
  2. Consumers process events at different times

Key-Components of an Event-Driven System:
1. Event Producer.
2. Event brokers (Transmits and store events).
3. Event Consumers(React to Events).
4. Event Storage (Log-based persistence for replaying events).
Architectural Patterns like CQRS and Event Sourcing enhance flexibility.

### Challenges in Event-Driven Architecture:
1. Eventual consistency: (No immediate data synchronisation) An upstream event may generate an event which the downstream team will take some time to reach. Idempotent consumers, compensating actions and carefully designed workflows are used for this.
2. Ordering Guarantees: Ensuring Events are process in sequence. Systems can reach a faulty state if events are not done in order, Systems like Kafka provide partition-based ordering guarantees and why many systems use version guarantees or sequencing in their application.
3. Fault Tolerance and retries (Handling failures gracefully): Retry mechanism, dead-letter queues and event replay capabilities are essential tools.
4. Debugging Complexity (Tracing events across microservices): strong looging and monitoring is required as many events can be triggered at once.

### Best Practices:
1. Use Idempotent event processing to avoid duplicates.
2. Implement dead-letter queues for failed messages. Failed events should be isolated rather than blocking the entire pipeline.
3. Choose the right event broker based on system need:
	1. Kafka: High throughput event streaming and long-term retention.
	2. RabbitMQ: Traditional message queuing patterns.
	3. AWS Event-bridge: cloud specific event routing.
4. Ensure event versioning to handle schema changes.


### Use Cases of Event-Driven Architecture:
1. Logging and Auditing: Track changes over time.
2. Real-time Notifications: Chat, apps.
3. Micro-services Decoupling: Independent scalability and fault tolerance.
4. IoT Systems: Sensor data processing.
5. E-commerce Order Processing: Order Placed -> Payment processed -> Inventory updated. Most common business actions.
