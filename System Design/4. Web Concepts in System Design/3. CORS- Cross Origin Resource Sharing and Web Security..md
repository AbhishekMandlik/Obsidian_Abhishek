Why CORS matters?
Browser enforces Same - Origini Policy, blocking cross-origin requests by default. You frontend is on frontend.com and API you are calling is on api.com so browser will block this so that malicious websites don't send request from users behalf to other websites.
Need for CORS:
1. Modern web apps rely on APIs hosted on different domains.
2. CORS allows secure cross-origin communication?
It allows servers to explicitly declare which origins are allowed to access their resources.
CORS selectively grants access to specific domains.
CORS is controlled by the server.

### How CORS Works: Request and Responses
1.  CORS is server-driven - the server must explicitly allows access.
2. Two types of requests:
	1. Simple request: GET, POST (without custom headers).
	2. Preflight requests: Needed for PUT, Delete, or custom headers. Browser as a caution sends a dummy request to check whether a server would allow these changes to occur and server responds with its CORS policy and if it allows only then the request is sent to the server.
3. CORS Header control:
	1. Access-Control-Allow-Origin (which origins can access these servers).
	2. Access-Control-Allow-Methods (allowed HTTP methods).
	3. Access-Control-Allow-Headers (custom headers that can be sent).

### Preflight Request and CORS headers
- Some requires preflight checks, sent via OPTIONs requests.
- Browser first sends a preflight requests before making the actual request.\
- If server responds via a valid CORS headers the browser allows the actual request.
- Key Headers:
	- Access-Control-Allow-Origin: https://example.com
	- Access-Control-Allow-Methods: GET, POST.
	- Access-Control-Allow-Headers: Authorisation, Content-Type.

### Security Risks and Common Misconfigurations
1. Common Security risks:
	1. Overly permissive CORS:  Access-Control-Allow-Origin: *
	2. Access-Control-Allow-Credentials: true with * origin.
	3. Exposing sensitive APIs via improper CORS settings.
2. Mitigation Strategies:
	1. Use whitelist of trusted origins instead of " * ".
	2. Set correct CORS policies for different API endpoints.
	3. Use reverse proxies or API Gateways to handle CORS securely.


### Handling CORS in APIs (REST and GraphQL)
CORS in REST APIs:
1. JSON- based APIs commonly use CORS.
2. Configure headers properly in backend frameworks(Express.js, Spring Boot, Django)

CORS in GraphQL APIs:
1. GraphQL APIs also need CORS handling since they operate over HTTP.
2. Preflight requests occur due to complex queries and mutation.

It is browser event handled by server and does not depend on which type of API are we using. So for both CORS should be implemented properly.

### Alternative to CORS and Role of API Gateways.
Alternatives to CORS for Cross-Origin Requests:
1. Reverse proxy:
	1. Forwards clients requests to the backend, bypassing browser CORS restrictions, Like Nginx proxying to a backend API.
2. API Gateway Handling CORS:
	1. Centralised control of CORS policies for multiple services.
	2. Example: AWS API Gateway configuring allowed origins.
To the browser when routing through a reverse proxies feels like all the requests are coming from the same origin hence many issues are solved. Gateways can define the policies, allowed origin endpoints. It improves security, scalability governance and preflight request handling(not having increased threshold).
#### How API Gateways and Reverse Proxies Help?
1. Reverse Proxies handle cross-origin requests internally to avoid CORS issues.
2. API Gateways enforce CORS policies centrally, ensuring security and consistency.
3. Both improve performance by reducing unnecessary browser pre-flight requests.
