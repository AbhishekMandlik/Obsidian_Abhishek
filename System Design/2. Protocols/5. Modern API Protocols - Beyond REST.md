Limitations of REST APIs:
1. In Rest Server decides the shape of the response. This can lead to over-fetching or under-fetching which increases the network overhead.
2. High Latency as multiple requests might be needed for complex tasks.
3. Not Optimised for real-time communication as Polling will be required. (Extra traffic)

### gRPC and GraphQL
1. gRPC: Service to service communication
	1. Instead of large JSON payloads, It uses compact binary messages and HTTP2 which reduces overhead --> lower latency. 
	2. It supports streaming natively for real time communication
	3. Fast, Binary, micro-services focused.
	4. Speed optimisation.
2. GraphQL: Rather than exposing multiple endpoints with fixed responses it allows a client to describe exactly what data it needs in a single request. Important to reduce network call and payload size that can directly improve the user experience. It optimises communication in clients and APIs.
	1. Flexible query language.
	2. JSON-based
	3. frontend-optimised

### gRPC
build on HTTP/2
- It allows multiplexed requests (multiple calls over one connection)
- Efficient streaming enabled. Instead of constantly opening a new request, a client and server can maintain a long-lived connection. Full duplex communication.
- Compression(small payload size).
- Uses Protocol Buffers(Protobuf) for fast serialisation. {Smaller and faster than JSON}

#### Use Cases:
1. Micro-services - Fast inter-service communication.
2.  Real-time streaming - Full duplex bidirectional data transfer.
3. IoT and Low-bandwidth applications - Efficient binary communication.
4. Multi-language ecosystems - Auto generated client and server code. A single Protobuf contract can generate client and server code for different technology stacks, which ensures consistent communication without teams manually maintaining SDKs.

### GraphQL
- It has one endpoints where client specify the data they need.
- GraphQL Schema defines types and relationships between data. This is maintained by both the frontend and backend teams.
- Client send queries -> GraphQL server resolves fields dynamically. It does not return a predefined payload. It gives more flexibility.
- Tradeoff is that server takes on more time and overhead resolving those queries. Schema driven API.
#### Use Cases:
1. Frontend Optimisation- Client fetch exactly what they need.
2. Reducing API Request - One query replaces multiple REST calls which reduces latency which is much essential in mobile payload.
3. Mobile and web apps - Handle slow networks and multiple data sources which will generally take multiple REST API calls. Low bandwidth used.
4. Aggregating Data from Multiple Services - Simplifies fetching data from different databases or APIs.
Most important where client demand is changing or data is coming from different sources having different payloads and need resolving as we process information.
