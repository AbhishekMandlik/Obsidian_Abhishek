All systems generate and consume data -- storing it is essential. It impacts performance, reliability and cost. Persistent storage enable everything from user profiles to search history to analytics.
### Structured vs. Unstructured Data.
- Structured: Rows/ columns in predefined schema.
- Unstructured: No schema, flexible format (e.g. images, videos, logs).

### Categories of Storage
- Database Storage (SQL/NoSQL).
- Objects storage (S3): It stores objects that can scale to billions of items. Durability and scalability matter more than latency or overhead.
- File storage(NFS): It is useful when multiple applications need shared access to the same files through a standardised file system.
- Block Storage: Storage on lowest level like disk.

### Storage properties
1. Durability: Data persists even after failures.
2. Availability: Data can be accessed when needed.
3. Consistency: Every read returns most recent writes.
4. Atomicity: Operations are all-or-nothing(relevant in transactional requests).

### Trade-offs in Storage Design
Scalability vs. Reliability vs. Performance
Growth vs. Reliability vs Speed.
Reliability store data in multiple places which can increase latency.

### The CAP Theorem
In any distributed system, you can only fully guarantee 2 of the 3:
1. Consistency: Every read gets the latest write.
2. Availability: Every Request receives a response.
3. Partition Tolerance: System continues despite network failures.
No system can have all 3 at the same time.
```
Since network partitions are unavoidable especially at scale, real world systems must choos between consistency & availability during a partition.
```

### Types of Systems Based on CAP Trade-offs
1. CP System:
	1. Prioritises data correctness over availability.
	2. During a partition the system may reject requests to avoid inconsistent reads.
	3. Not always available, but when it is -- data is guaranteed to be correct.
	4. Eg. HBase, strongly consistent. If a node cant confirm a write across replicas, it wont serve it -- even if it means being unavailable briefly. Mostly used in financial systems.
2. AP System: 
	1. Prioritises system uptime over consistency.
	2. During a partition, the system will serve requests even if they return stale or eventually consistent data.
	3. DynamoDB, Inspired by Amazons Dynamo model, which uses eventually consistency by default for high availability. 
	4. Social media feds, product catalogs, content delivery.
3. CA System: "The Unicorn"
	1. Only possible if no network partitions ever occur. i.e. in a single node or tightly coupled systems. 
	2. Not achievable in distributed systems that need to tolerate network faults.
	3. Eg. Relational Databases in standalone mode(not distributed) could be CA.

### Real-World Use cases
- E-commerce: Product catalog(structured), images(object).
- Streaming services: Media files(object), user data(NoSQL).
- Log aggregation: Time-series/columnar DB(Recent logs) or object storage(archived logs) at much lower cost in S3.
