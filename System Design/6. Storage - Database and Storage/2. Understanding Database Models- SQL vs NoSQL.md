Database is a structured way to store, retrieve and manage data. Supports persistent storage and efficient querying. Core Component in backend systems.

### Relational Database
1. Data stored in rows and columns.
2. Enforces Strict schema.
3. Uses SQL or other language for queries, which makes searching efficient.

### Core Concepts of RDB
1. Schemas: Predefined structure(table, columns, data types).
2. Joins: Combines data across multiple table.
3. ACID Properties:
	1. Atomicity: All or nothing. It ensures a transaction completes fully or not at all.
	2. Consistency: It keeps data valid according to defined rules.
	3. Isolation: It prevents concurrent transactions from corrupting.
	4. Durability: Changes Survive System failures.
### Limitations:
Not ideal for:
1. Rapidly changing or schema-less data.
2. Large-scale horizontal scaling.
3. Flexible or nested data,

## Intro to NoSQL
- Designed for flexibility.
- Schema-less or dynamic Schema.
- Types:
	- Document (mongoDB). Rich JSON like structuresand are ideal for flexible application data.
	- Key-Value(Redis, DynamoDB). Extremely fast lookup and low latency.
	- Columnar(Cassandra, HBase). High write throughput and large-scale distributed workloads.
	- Graph(Neo4j). Traversing complex relationships between entities.

No SQL Deep Dive:
 - Document (mongoDB):
	 - Rich JSON like structures and are ideal for flexible application data.
	 - Key value pairs and nesting is supported.
	 - Ideal for content management and user profiles.
 - Key-Value(Redis, DynamoDB):
	 - Extremely fast key-based lookup and low latency.
	 - High performance.
	 - Redis stays in Memory unlike postgres which stays in Storage, which can make postgres much cheaper but it has connections limit hence we can't use it as cache even if latency is little high only.
 - Columnar(Cassandra, HBase):
	 - High write throughput and large-scale distributed workloads.
	 - Store data by column and not by row.
	 - Optimised for analytical queries over large datasets.
 - Graph(Neo4j). 
	 - Traversing complex relationships between entities.
	 - Store Entities and relationships at nodes and edges.
	 - Efficient for highly connected data like social networks.

### Base properties in NoSQL
- Basically Available: Always return a response even if it is stale. Maintaining perfect availability and consistency is difficult. In BASE model Edge cases don't get updated data for all time.
- Soft State: Systems state may change over time.
- Eventually consistent: Data will be consistent... eventually.

### CAP Theorem - Revisited
Consistency, Availability, Partition Tolerance.
SQL tends towards CP, NoSQL systems often choose AP or BASE.

### When to Use What?
1. SQL
	1. Complex queries and relationships.
	2. Strong Consistency needed.
	3. Structured and well-known schema.
	4. Banking, ERP, Inventory Systems.
2. No SQL:
	1. High scalability.
	2. Flexible or evolving Data Structure.
	3. Low-Latency/ high volume operations
	4. IoT, Recommendation Systems, Caching and logs.

Many systems today use both SQL and NoSQL DB technology -- Polyglot Persistence.
